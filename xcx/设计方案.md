# 小程序端设计方案（微信 / 支付宝 / 抖音）

> 上游依据：`设计实录.md` 第 1 节「产品形态与多端战略」把微信小程序列为 P1；本方案在此基础上扩到**三端同构**，并明确与 Web 端共用同一套分析引擎。
> 施工记录、逐项验证写进 `修复记录文档.md`；本文件只讲**怎么设计、为什么这么设计**。

---

## 1. 目标与范围

| 项 | 内容 |
|---|---|
| 交付目标 | 三端小程序：**微信（优先，先跑通全流程）** → 支付宝 → 抖音，功能与 Web 端一致（体检 / 地图 / 报告） |
| 复用原则 | 分析引擎 `src/core` **一行不改**；地图与网络能力全部通过「适配器 + 平台层」注入 |
| 一期范围 | 定位选点 → 一键体检（进度可见）→ 报告（总分/维度/告警/盲区/补建建议）→ 地图（等时圈热力 + 设施 + 盲区 + 补建点）→ 自己的标记盲区 → AI 诊断 |
| 二期范围 | 登录/注册与我的标记云端同步、报告分享图、订阅消息、步行导航唤起、管理员配置只读 |
| 不在范围 | 管理员控制台（仍留在 Web/Electron 端）、AI 语音导航（Web 端专有） |

## 2. 一核三端：整体架构

```
        ┌──────────────────── 各端「壳」（不可复用） ────────────────────┐
        │  微信 wxml/wxss/project.config.json                           │
        │  支付宝 axml/acss/mini.project.json                           │
        │  抖音   ttml/ttss/project.config.json                         │
        └───────────────────────────┬──────────────────────────────────┘
                                    │ 视图层分端（同一套页面逻辑生成的模板）
        ┌───────────────────────────▼──────────────────────────────────┐
        │  xcx/common  三端共享层（纯 JS，零平台 API 直调）              │
        │   plat.js（平台探测+统一 API） │ tijian.js（体检编排）           │
        │   adapters/bmapXcx.js（provider）│ adapters/shuiyuXcx.js（水域）│
        │   ai.js（AI 诊断）│ zhuangTai.js（状态）│ bidui.js（抽稀/换算）  │
        └───────────────────────────┬──────────────────────────────────┘
                                    │ import（零改写）
        ┌───────────────────────────▼──────────────────────────────────┐
        │  src/core  分析引擎（纯 JS，零 DOM / 零网络）                  │
        │  pipeline → poi → isochrone → blindspot → scoring → scheduler │
        └───────────────────────────┬──────────────────────────────────┘
                                    │ 只走自有服务端（HTTPS 单一域名）
        ┌───────────────────────────▼──────────────────────────────────┐
        │  fuwuqi/fuwu-qi.mjs：/api · /bmapapi · /airelay · /shuiyu      │
        │  服务端代持百度服务端 AK、AI 密钥、水域缓存                     │
        └──────────────────────────────────────────────────────────────┘
```

**三层各自的边界**

1. **`src/core`（引擎）**：坐标系一律 WGS-84，不碰 DOM、不碰网络（`pipeline.js:56` 明确「core 不碰网络，保持跨端可复用」）。小程序直接 `import` 这批文件，**不做任何改动**。
2. **`xcx/common`（共享层）**：把平台差异收敛到 `plat.js` 一个文件里（请求、存储、定位、地图交互、分享、提示），页面逻辑与适配器只认 `plat.xxx()`，所以同一份页面逻辑能跑在三端。
3. **各端工程目录**：只保留**必须分端**的东西——视图模板（wxml/axml/ttml）、样式、工程配置、分包配置、地图组件的属性差异。

## 3. 关键设计决策

| 决策 | 选择 | 为什么不选另一条 |
|---|---|---|
| 地图组件 | **各端原生 `<map>`**（微信/支付宝/抖音均有），坐标系 GCJ-02 | 百度小程序 SDK 只覆盖微信端、需另外申请小程序 AK，且三端 SDK 不一致；原生 `<map>` 三端都能用、显示不耗 AK |
| 坐标系 | 边界转换：**引擎内 WGS-84 ↔ 渲染 GCJ-02** | 复用 `src/core/geo/zuobiao.js` 现成的 `wgs84ZhuanGcj02 / gcj02ZhuanWgs84`（对向迭代 <1m），不必改引擎 |
| 密钥 | **端上零密钥**：百度服务端 AK、AI 密钥全部留在服务端 | 小程序包体可被反编译，AK 一旦下发就等于公开；同时省掉「在小程序后台配一堆地图域名」 |
| 网络出口 | **百度接口双通道**：默认直连（`peizhi.bmapAk`，微信自动带 `servicewechat` Referer）→ 失败自动退自有服务端 `/bmapapi`；账号/AI/水域一律走服务端 | 直连让小程序不依赖任何本地服务即可体检（演示稳）；服务端通道端上零密钥 + 多 AK 轮换（生产首选）。两者互为备份，任一条的失败原因都会一起报出来 |
| 首屏 | **地图页即第一屏**，操作与结论以浮层承载（顶部定位条 + 图层胶囊 + 底部主卡） | 产品本身就是「看这片区域覆盖得怎么样」，先给结论画面比先给表单更贴合使用场景 |
| 视觉 | **一套设计语言集中在 `miniprogram/app.wxss`**（白卡片 + 低扩散投影 + 绿主色 + 大号分数；页面结构统一为「`.ka` 卡片 + `.qu-biao` 竖条标题 + `.an` 三档按钮」） | 三端共用同一份样式真源，同步脚本复制成 `acss`/`ttss`；改一处三端一致，不会各写一套导致观感漂移 |
| AI 对齐 | **提示词与本地规则逐字复用**（诊断 / 在线问答 / 选点导航三块），只把 `fetch` 换成 `plat.request`；平台差异只保留「导航唤起系统地图」 | 网页端 AI 的价值在大模型提示词与上下文注入，重写一遍必然漂移；自检里直接做「两边 `benDiZhenDuan()` 输出全等 + 7 处关键提示句逐字比对」 |
| 页面逻辑 | **逻辑共享、视图分端**：`common/pages/*.js` 里写 `Page({...})`，各端页面目录只放模板与样式 + 一行导入 | 三份近乎相同的页面 JS 手工维护必然漂移；模板差异（`wx:` / `a:` / `tt:`）用同步脚本机械转换 |
| 依赖 | **零 npm 依赖**（引擎与共享层都是原生 ESM） | 小程序不支持 Node 包解析，少一层构建就少一类「换个工具就打不开」的坑 |
| 代码同步 | `scripts/tongbu-xcx.mjs`：`src/core`（纯算法子集）→ 各端 `lib/core`；`xcx/common` → 各端 `lib/common`；微信视图 → 支付宝/抖音视图 | 单一真源，避免「Web 修了 bug、小程序没跟上」 |

> 与 `设计实录.md` 第 11 节的差异说明：那里写的是「小程序 adapter 换百度小程序地图组件」。本轮因要一次覆盖微信/支付宝/抖音三端，改为**原生地图组件 + 坐标边界转换**；引擎复用这一条不变。若后续只做微信端且要求与 Web 端底图完全一致，可再加一个 `bmapWx` 适配器并行（`plat.js` 已是可插拔结构）。

## 6. 一次体检的数据流（时序）

```
用户点「开始体检」
  → plat.getLocation()                定位（微信返回 GCJ-02，取 gcj02 型）
  → zuobiao.gcj02ZhuanWgs84()         转成引擎坐标（WGS-84）
  → /bmapapi/reverse_geocoding/v3     取社区名（经服务端代持 AK）
  → shuiyuXcx.huoShuiYu(中心)         取水域（/shuiyu，失败则本轮不避让）
  → yunXingTijian(provider, canShu, {jinDu, peiZhi, shuiYu, huanCun})
        ├ provider.searchPoi       → /bmapapi/place/v2/search（按关键词并发，令牌桶限流）
        ├ provider.walkingRoute    → /bmapapi/direction/v2/walking
        ├ provider.routeMatrix     → /bmapapi/routematrix/v2/walking（批量，失败自动降级算路）
        ├ 等时圈：扇形采样 → 插值 → Marching Squares → 路网吸附（水面格标不可达）
        ├ 盲区：候选网格 → 精算 → 聚类 → 补建点
        └ 评分：六维得分 → 总分 → 等级 → 建议
  → zhuangTai.cunBaoGao(report)       内存常驻 + 存储里存「瘦身摘要」（冷启动可看摘要）
  → 报告页/地图页读取同一份 report 渲染
```

进度回调 `jinDu(p, jieduan)` 直接驱动首页进度条；`p` 为 0~1，`jieduan ∈ {sousuo, caiyang, mangqu, ...}`，映射成中文阶段文案。

## 7. 地图渲染方案（三端一致的观感）

| 图层 | 数据来源 | 渲染 |
|---|---|---|
| 等时圈热力 3 层 | `report.dengShiQuan.ceng`（按 miao 倒序） | `<map>` 的 `polygons`，色板与 Web 端一致（300 绿 / 600 蓝 / 900 红），透明度 0.34/0.22/0.12；**每环抽稀到 ≤180 点**（`bidui.chouXi`） |
| 跨水面虚线 | `report.dengShiQuan.shuiDuan` | 原生 map 无虚线折线能力 → 用 `polyline` 的 `dottedLine: true`；仍不行则降级为细实线（差异在文档里注明） |
| 设施散点 | `report.poiSet.fenleiSet` | `markers`，按维度用不同颜色圆点（图标用本地小图，避免网络图床） |
| 盲区 | `report.mangquList` | `circles`（半径由 `areaM2` 折算），重度红 / 轻度橙 |
| 补建点 | `mangquList[].buJianDian` | `markers` 绿 ✚，点 `markertap` 弹建议浮层 |
| 中心点 | `report.zhongXin` | `markers` 图钉（唯一带 `callout` 常显的） |
| 步行路线 | 现场调 `walkingRoute` | `polyline`，虚线 |

**性能**：小程序 `setData` 传输大数组代价高，等时圈点数按「保形抽稀」（步长 = 周长/180，且保留拐点）压到 180 点/环以内；设施散点单类上限 120 个；切换图层只 `setData` 变化的键。

## 10. 风险与对策

| 风险 | 对策 |
|---|---|
| 小程序主包 2MB 限制 | 引擎纯 JS 约 150KB；不引 npm 依赖；设施图标用本地小图；必要时把地图页放分包 |
| 百度 Web 服务配额被体检打光 | 服务端多 AK 轮换（沿用 Web 端机制）+ 引擎三级缓存 + 密度档位（快/标准/精细 = 64/96/128 网格） |
| 坐标系错位（500m 级） | 引擎恒 WGS-84、渲染前统一转 GCJ-02；所有出入站点只在一处转换（`adapters/*`），页面不直接换算 |
| 三端 API 差异漂移 | 差异只在 `plat.*.js` 与视图模板；同步脚本一次生成，`README.md` 附带「三端差异对照表」 |
| 大数组 `setData` 卡顿 | 抽稀 + 分层 `setData` + 图层开关；盲区/设施分批渲染 |
| 水域数据取不到 | 服务端缓存 + 预置样例文件；取不到就按「本轮不避让」继续，报告里如实提示（与 Web 端行为一致） |
| 真机预览需 HTTPS | 服务端用 cloudflared/ngrok 暴露（工程已有内网穿透习惯，见 `设计实录.md` 第 14 节），小程序后台把该域名加白名单 |
